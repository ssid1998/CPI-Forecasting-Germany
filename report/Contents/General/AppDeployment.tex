\chapter{Application Deployment}
\label{ch:app-deployment}

\section{Application Description}

The deployed application is a Streamlit dashboard for interactive inspection of Germany's CPI forecasts. Its purpose is not to retrain models online, but to present the outputs of the offline forecasting pipeline in an accessible and reproducible way. Users can select a forecasting model, view actual and predicted CPI values, inspect confidence intervals, and compare evaluation metrics.

This deployment choice matters for the project because it turns the forecasting work from a static script output into a reusable analytical interface. A report table is sufficient to document who won the model comparison, but it is less useful for understanding where forecasts diverge over time, how confidence intervals widen, or how the relative performance of the models appears visually on the same holdout period. The dashboard therefore functions as the user-facing endpoint of the project: it does not replace the underlying modeling pipeline, but it makes the results easier to inspect, demonstrate, and interpret.

\section{Structure}

The application is implemented in \texttt{Code/app.py}. Its structure consists of four main parts: page configuration and introductory text, sidebar controls, metric and plot display, and explanatory sections.

\subsection{Sidebar Controls}

The sidebar is the primary interaction panel. It contains two dropdown selectors:

\begin{itemize}
    \item \textbf{Select Model:} A dropdown menu offering four options:
    \begin{itemize}
        \item \texttt{ARIMA (1,1,1)} -- displays the ARIMA forecast with confidence intervals
        \item \texttt{ETS (A,A,A)} -- displays the ETS forecast with confidence intervals
        \item \texttt{SARIMA (1,1,1)x(1,1,1,12)} -- displays the SARIMA forecast with confidence intervals
        \item \texttt{Compare All Models} -- overlays all three forecasts on the same chart for direct visual comparison
    \end{itemize}
    \item \textbf{Confidence Interval Level:} A dropdown allowing the user to select 80\%, 90\%, 95\%, 96\%, 97\%, 98\%, or 99\% confidence bands. The default is 95\%.
\end{itemize}

When the user selects an individual model, the dashboard loads the corresponding serialized \texttt{.joblib} file from \FILELOC{Code/saved\_models/}, regenerates the 24-step forecast, and displays the forecast curve together with the selected confidence band. When the user selects \texttt{Compare All Models}, the dashboard loads all three models simultaneously, computes their forecasts on the common test period, and renders an interactive Plotly chart with all forecast curves overlaid on the actual test data. This comparison mode is particularly useful because it allows the user to see immediately which model tracks the actual CPI path most closely.

\subsection{Dashboard Runtime Stages}

At a more detailed level, the dashboard separates responsibilities into a small number of understandable runtime stages:

\begin{enumerate}
    \item \textbf{Path resolution:} The application resolves paths relative to its own file location so that the CPI CSV and serialized models can be found reliably.
    \item \textbf{Data loading:} It loads the preprocessed CPI series and applies the same chronological split that is used in the offline evaluation.
    \item \textbf{Model mapping:} It maps the user-selected model name to the corresponding saved model artifact and generates forecasts and, where supported, confidence intervals.
    \item \textbf{Metric computation:} It computes or recomputes the evaluation metrics shown to the user and passes the results to the plotting and layout layer.
\end{enumerate}

This structure is simple enough for a student project, but also modular enough that future deployment features could be added without rewriting the whole application.

\section{Idea}

The main deployment idea is to separate modeling from presentation. Training and evaluation are performed once in the development pipeline, whereas the Streamlit app focuses on communicating the results. This improves usability because end users do not need to understand the internal forecasting scripts in order to inspect the outcomes.

This separation also improves reproducibility. Because the app consumes already-defined data and model artifacts, a user who launches the dashboard sees results that are traceable back to the same underlying repository pipeline described in the report. The deployment layer is therefore intentionally thin: it does not silently retune models, alter the holdout horizon, or introduce a second evaluation method. Its role is to expose the already-established analytical logic through an interactive interface.

\subsection{Model Comparison Mode}

When the user selects \texttt{Compare All Models} from the dropdown, the dashboard switches to comparison mode. In this mode, the sidebar remains the same, but the main area changes to display a metrics table highlighting the best-performing model and an interactive chart overlaying all three forecast curves on the same axes. This allows direct visual comparison of how ARIMA, ETS, and SARIMA diverge from the actual CPI path. The comparison mode is one of the most useful features of the dashboard because it makes the relative strengths and weaknesses of each model immediately visible without requiring the user to switch between individual model views manually.

\section{ML Pipeline}

The deployment layer consumes the outputs of the machine-learning pipeline rather than re-executing the full training stage. It uses the cleaned CPI series, the serialized model artifacts, and the metric logic already established in the development stage. This ensures consistency between the values shown in the dashboard and the values documented in the report.

In KDD terms, the deployment chapter belongs after data selection, preprocessing, transformation, mining, and interpretation because it depends on the artifacts created there. The app requires a valid CPI data file, successfully trained \texttt{.joblib} models, and evaluation logic that is already known to be correct. This dependency chain should be made explicit because it explains why deployment cannot be treated as an isolated front-end exercise. If the saved models are missing or inconsistent with the current data file, the deployment layer will fail or display misleading results even if the user interface itself is implemented correctly.

\section{Program Readability and Modules}

The application code is reasonably readable because it separates configuration, data loading, model-file mapping, forecast generation, and explanatory text into recognizable blocks. The path handling is more robust than in some of the training scripts because \texttt{app.py} resolves its main directories relative to its own file location.

This readability is relevant to deployment quality because a dashboard often becomes the part of a project that other people interact with most frequently. In \FILELOC{Code/app.py}, the visible configuration options, the loading logic, the metric computation, and the plotting code are still located in one file, but they are organized in a sufficiently clear order that future changes remain realistic. The current structure is therefore acceptable for the project scope, although a more production-oriented version would likely separate the user-interface layer from the forecasting-service layer even more explicitly.

\section{Parameter Handling}

The dashboard exposes only deployment-relevant parameters to the user. These are the model choice and the confidence-interval level. Forecast horizon and evaluation horizon remain fixed in the underlying application logic, which preserves comparability with the report results.

This restricted parameter design is deliberate rather than accidental. Allowing the user to alter the model and uncertainty level supports meaningful interaction, while keeping the test horizon fixed protects the comparability of the results. If the app allowed arbitrary retraining windows or different evaluation horizons at runtime, the deployment view would no longer correspond directly to the report's documented evaluation setup. The current parameter handling therefore favors interpretability and reproducibility over unrestricted configurability.

\section{Error and Message Handling}

If model files are missing, the application shows a visible error message and instructs the user to run the training pipeline first. If confidence intervals cannot be calculated, the app raises a warning instead of terminating the session. In addition, the interface uses spinners, metric descriptions, and expandable explanations to guide the user through the interpretation of the results.

The deployment layer is therefore moderately robust, but not yet fully hardened. It handles several expected failure modes in a user-visible way, especially missing artifacts and interval-calculation problems. However, the app still depends on the surrounding file structure remaining stable and on the serialized models being compatible with the installed Python environment. This means that deployment robustness currently relies more on disciplined project maintenance than on a fully isolated packaging strategy. For the scope of this report, that limitation should be stated clearly rather than hidden.

\subsection{CI/CD Integration}

While the project does not currently use a continuous-integration platform such as GitHub Actions or GitLab CI, the test suite is structured so that it could be integrated into one with minimal effort. A typical CI/CD workflow for this project would consist of the following steps:

\begin{enumerate}
    \item \textbf{Environment setup:} Install Python dependencies from \FILELOC{Code/requirements.txt}.
    \item \textbf{Linting:} Run \texttt{flake8} or \texttt{ruff} to check code style and catch syntax issues.
    \item \textbf{Unit tests:} Execute \texttt{pytest Code/tests/} to verify data loading, model fitting, and monitoring logic.
    \item \textbf{Coverage check:} Use \texttt{coverage.py} to ensure that critical paths in \FILELOC{Code/src/} are exercised by the test suite.
    \item \textbf{Pipeline execution:} Run \FILELOC{Code/src/modeling\_pipeline.py} to confirm that the full training and evaluation workflow completes without error.
    \item \textbf{Artifact verification:} Check that \FILELOC{Code/saved\_models/} and \FILELOC{Code/plots/} contain the expected files after pipeline execution.
\end{enumerate}

\section{Deployment Test Protocol}

Formal automated application tests are still limited, but the deployment can be validated through a practical protocol: confirm that the saved model files exist, start Streamlit successfully, verify that each model can be loaded, and check that the dashboard renders charts and metrics without runtime failure.

A more explicit deployment test protocol can be stated as follows. First, verify that the CPI CSV file and all expected model artifacts exist in their designated directories. Second, launch the dashboard from the intended working directory and confirm that the application starts without import or path errors. Third, test each model option individually and then the comparison mode so that every loading branch in \texttt{app.py} is exercised. Fourth, change the confidence-interval selector and verify that the chart updates without breaking the metric display. Fifth, compare at least one visible metric set against the offline evaluation outputs to confirm consistency. This protocol is still lightweight, but it provides a clearer bridge between development validation and practical deployment testing.

Future automated deployment tests should focus on the most failure-prone paths. These include checking whether the saved models can be deserialized, whether the dashboard still renders when confidence intervals are unavailable, and whether key user-interface elements appear after launch. Such tests would strengthen the report's deployment section because they would transform the current manual validation process into a repeatable testable deployment workflow.
